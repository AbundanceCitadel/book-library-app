### 2026-07-24 — Stage 0

1. **Expanded category taxonomy from 6 to 12 categories.** The original list didn't have a home for philosophy/psychology, finance, health, fiction, science/tech, or general biographies (non-business, non-religious). A library of "hundreds of books across many genres" would hit these quickly. Added: Business Strategy stays separate from Business (strategy books are more executive/analytical than general business), Philosophy & Psychology, Finance & Investing, Health & Wellness, Fiction & Literature, Science & Technology, and Biographies — Other (catch-all for bios that aren't business or religious figures).
2. **Language is a filter field, not a category**, per the master prompt's explicit instruction — implemented as a `language` enum field (`en` / `vi` / `other`) on every book, independent of `categories`.
3. **Data format: JSON only, not Markdown.** The master prompt allowed either. Chose pure JSON per book because it's trivially importable into Next.js with type safety, easy to validate against a schema, and avoids parsing two formats. A JSON Schema doc (`docs/SCHEMA.md`) is the source of truth.
4. **Included personalization fields (`readStatus`, `personalNotes`, `rating`) in the schema now**, defaulted to empty/unread, even though the UI for them doesn't ship until Stage 11. Rationale: adding fields to already-written book JSON files later is more tedious than reserving them now at zero cost.
5. **Project folder name: `book-library-app/`**, created inside the "1. BOOKS LIBRARY" folder Thai already had mounted, rather than a new top-level folder — keeps everything in the location Thai already treats as this project's home.
6. **Chapter/section structure uses a `structureType` field (`"chapters"` or `"parts"`)** on each book, since the master prompt notes some books are structured as Parts rather than Chapters. The UI will render whichever the book uses.

### 2026-07-24 — Stage 3 (Design System)

12. **Two-font system: sans for UI chrome, serif (Tailwind's default system serif stack) for reading content.** No webfont download (Google Fonts etc.) — kept it to system stacks only, consistent with the "avoid extra install/network weight" approach from decisions #8–9, and it gives the app a distinct "book" feel for summaries/quotes/lessons vs. app-y nav and labels. Applied via a `.prose-reading` utility class in `globals.css` rather than repeating classes inline everywhere.
13. **Single warm amber/terracotta accent color** (`accent` scale added to `tailwind.config.ts`) rather than a cool blue/indigo or a rainbow of per-category colors. Rationale: a personal reading app should feel calm and "paper-like," not like a SaaS dashboard; one accent used sparingly (links, active states, category chip highlight) keeps 12 categories from feeling like a color-coded mess. Categories are instead distinguished by an emoji icon + label.
14. **Emoji icons per category instead of an icon library** (e.g. lucide-react). Zero new dependency, zero bundle weight, renders everywhere without a font/SVG sprite to manage. Documented the exact icon-to-category mapping in `docs/DESIGN_SYSTEM.md` and `lib/books.ts` (`CATEGORY_ICONS`) so it's easy to swap for a proper icon set later if the emoji rendering ever looks inconsistent across platforms.
15. **Dark/light mode: kept the existing Tailwind `class` strategy, added a 3-state toggle (light/dark/system) persisted to `localStorage`, plus a no-flash inline script in `app/layout.tsx`'s `<head>`.** The toggle lives in a new shared `Header` component rendered from the root layout so it's available on every page without per-page wiring.
16. **Mobile-first layout rules formalized in `docs/DESIGN_SYSTEM.md`**: `max-w-2xl` for the reading-focused book detail page (optimal line length), `max-w-5xl` for browse pages (home/category grids), 44px minimum touch targets via a `.tap-target` utility, and `env(safe-area-inset-*)` padding added now ahead of Stage 5 PWA work so it doesn't need revisiting later.

### 2026-07-24 — Stage 5 (PWA Installability)

22. **Generated app icons programmatically (PIL) instead of commissioning/sourcing artwork.** A simple flat "open book" glyph in the Stage 3 accent color (`#c97f2b`) on a solid full-bleed background, at 512/192/apple-touch/favicon sizes plus a dedicated maskable variant with extra safe-zone padding. Zero-dependency, on-brand, and good enough for a personal-use app; easy to swap for custom artwork later by replacing files in `public/icons/` (filenames/sizes are stable, referenced from `public/manifest.json` and `app/layout.tsx`).
23. **Maskable icon uses a plain full-bleed square background, not a pre-rounded shape.** First attempt baked rounded corners into the maskable PNG before flattening transparency to RGB, which produced black corner artifacts (transparent corners default to black on `.convert("RGB")`). Fixed by drawing all icons full-bleed with no baked-in rounding — correct practice per the maskable-icon spec, since the OS applies its own mask shape (circle, squircle, etc.) and expects the safe-zone padding, not the corner rounding, to protect the artwork.
24. **Hand-wrote `public/sw.js` instead of adding `next-pwa` or Workbox as a dependency.** Consistent with the project's minimal-dependency stance (decisions #8, #9, #14). Strategy: network-first with cache fallback for page navigations (falls back to a static `/offline` page if nothing's cached yet), cache-first for hashed `_next/static/*` assets and icons. Trade-off: no automatic build-time precache manifest of hashed asset URLs (that's what next-pwa/Workbox's webpack plugin normally generates) — `CACHE_VERSION` in `sw.js` has to be bumped manually when precached content should invalidate. Acceptable for a personal app with infrequent deploys; revisit if this becomes a source of stale-content bugs.
25. **Service worker registration is gated to `NODE_ENV === "production"`** (`app/components/ServiceWorkerRegister.tsx`) so `next dev` never caches responses — a caching SW in dev mode is a well-known source of "why isn't my change showing up" confusion.
26. **`theme_color` in `manifest.json` is a single fixed brand color** (`#c97f2b`, the accent) rather than light/dark-aware, since the manifest spec only supports one static value (unlike the `<meta name="theme-color">` tags in `app/layout.tsx`, which already vary by `prefers-color-scheme` from Stage 3). This only affects the OS chrome color when the app is launched standalone from the home screen.
27. **Verified installability signals from the sandbox (manifest served correctly, icons resolve, `sw.js` served with the right content-type, offline page builds) but could not verify the actual "Add to Home Screen" prompt or live offline behavior**, since that requires a real mobile browser (Chrome/Safari) hitting a deployed HTTPS URL — not available in this sandbox. Once Vercel deploy is unblocked (Stage 2 note), worth a quick manual check on Thai's phone.
